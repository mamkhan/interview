# ADR-007: Testing Standards

Status: Accepted (review of 2026-09-07); amended 2026-09-07: hand-written fakes are the one mocking style (rail cleanup decision B7), and test databases are built by `MigrateAsync()` per the ADR-003 amendment; amended 2026-09-17: each tier is its own test project, routed in the pipeline by project name; amended 2026-10-12: three tiers, the AppHost boot tier removed; the acceptance suite runs locally before every push and against dev as the gate; one feature test per host role; each pipeline runs only its own tests
Date: 2026-09-07
Evidence: the proof of concept's `CLAUDE.md` and the house `tdd` skill (the practice that delivered the rail at a 98% match rate); the build baseline's engineering practices

## Context

The team standard is test-first development with acceptance evidence gating every deploy, practised on the rail through four test tiers and a set of rules that were earned rather than chosen. This ADR adopts them as the platform standard so the Phase 3 scaffolding, the pipeline gates and every new module start from the same contract.

## Decision

**Method: classicist (Detroit school) test-driven development**, red-green-refactor in vertical slices (one test, one implementation, repeat). Tests are the living specification: they assert observable behaviour and state, never interaction with internals; domain objects are always real; test doubles appear only at cross-boundary seams (clock, bus, stores).

**Stack**: xunit v3, AwesomeAssertions, Testcontainers. FluentAssertions is not used (its version 8 licence change is why the rail moved to the fork). Test doubles are hand-written fakes; no mocking library (the rail's B7 cleanup made this the one style, and it is what keeps tests state-based). A coverage collector is referenced only if coverage is actually collected in the pipeline.

**Four tiers, in pipeline order**:

| Tier | Scope | Infrastructure |
|---|---|---|
| Unit | Domain and Application behaviour, no I/O | None |
| Integration | Repositories, consumers, projections against real stores | One shared container stack (SQL Server, Service Bus emulator, Azurite) started by whichever assembly arrives first via Testcontainers reuse |
| Acceptance | Replays real production market files and asserts outputs against V1's actual recorded production output | Own containers; scenario assets generated by tooling with the extract's origin recorded |
| AppHost boot | Boots the real application graph with no configuration overrides | Own containers; the only guard against topic, subscription and connection wiring drift |

**Rules with teeth**, carried verbatim from the rail:

1. **Expected values are frozen literals derived offline** (by hand, a throwaway script, or a trusted external source such as V1's real output), recorded with their derivation. A test that computes its expectation with the production formula proves nothing. Structural asserts between outputs are fine; at least one test per scenario pins outputs to literals.
2. **One scenario, one `When<scenario>` class**; methods named after the observable outcome; the constructor wires the system under test.
3. **Builders and personas live in the shared test library** (`building-blocks/tests-shared`), alongside the container fixtures; the container builder configuration stays byte-identical across suites (the configuration hash is what makes them share a stack), and each test class gets its own database plus topic and blob prefixes rather than doing cleanup.
4. **Integration tests use real stores, never in-memory substitutes.**
5. **Acceptance tests gate the deploy.** A change whose acceptance tier is red or unfinished does not deploy; finishing the tests is part of the change.
6. **A temporal-precision test per table**: at least one pinned timestamp that legacy `DATETIME` precision cannot represent, so the ADR-003 typing rule cannot silently regress.
7. **A tier is a project, not a namespace** (amendment of 2026-09-17). `<X>.UnitTests` holds the unit tier and `<X>.IntegrationTests` the container tier, and only the latter references the shared fixtures: a unit test that reaches for a container fails to compile rather than quietly starting Docker. The pipeline routes on the project name, so the unit job needs no filter and no Docker. A helper both tiers need is duplicated or promoted to the shared test library; it is never reached across the boundary.

**Coverage judgement**: test effort concentrates on critical paths, calculation correctness and the awkward market cases (revisions, withdrawals, replay); enumerating trivial edge cases is not the standard. The `tdd` skill is ported into the platform repository in Phase 3 and is the working reference, not a suggestion.

## Consequences

- The pipeline (Phase 4) runs the tiers in the stated order and the acceptance gate is structural, not procedural.
- The shared-stack discipline makes the integration tier fast enough to run on every push, which is what keeps TDD honest under CI.
- The integration tier's assemblies run one after another: `SharedPlatformContainers` holds its lock only while starting, and its stale-stack drop would tear containers out from under a concurrent suite.
- Frozen-literal expectations make parity evidence auditable: every number in a test can be traced to its offline derivation.
- The standard is demanding for newcomers; the ported `tdd` skill, the scaffolded examples per tier (Phase 3) and `ONBOARDING.md` (Phase 6) are the mitigations.

## Amendment of 2026-10-12: three tiers, each behaviour asserted once

**Provenance.** The owner's test review of 2026-10-12 measured about 36 minutes from a push to dev's acceptance result: the platform pipeline re-ran every domain test before the domain pipeline ran them again, the AppHost boot job took about 5 minutes of a 2-agent pool, and the integration tier spent most of its 5 minutes rebuilding databases per test, waiting out fixed delays and repeating one class per message type. Most of what the boot tests asserted the acceptance suite already asserted against dev.

**Tiers.** The AppHost boot tier is removed; three tiers remain beside the architecture tests. **Unit** owns every rule that needs no I/O, including dispatch to registered strategies and the composition a role needs. **Integration** owns only what a real store or bus decides: repository SQL, constraints, locks and precision, storage formats, one feature test per host role that drives each of its consumers once on production subscription names, and dead-letter and redelivery proven once in the building blocks. **Acceptance** owns every feature end to end, from its real input to its observable output on the real wiring, and is the release gate. A behaviour is asserted in the cheapest tier that can prove it and not repeated in another.

**The local graph.** Developers and agents run the acceptance suite against `aspire start` before every push; that run replaces the boot tier as the guard for the local graph's wiring. No pipeline job boots an AppHost.

**Pipelines.** Each pipeline runs only its own tests, once per push: a domain pipeline its `domains/<domain>/tests/` projects, the platform pipeline `platform/src/tests/`. A domain pipeline also triggers on the building blocks and the contracts it consumes, so a shared change is tested and deployed with the domain. A test job fails when a matched project produced no results.

**What stands regardless**: classicist TDD, hand-written fakes, frozen literals, a tier per project, real stores in the integration tier, and the acceptance gate before production. The `testing-strategy` skill is the working reference for where a test goes.
